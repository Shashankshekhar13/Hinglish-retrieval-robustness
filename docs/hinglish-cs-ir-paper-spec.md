## 1. One-line pitch
Recent work shows retrievers break on code-switched queries, but it only studied
native-script languages. In romanized Hinglish, much of the damage comes from
**spelling variation** (nahi / nahin / nhi), not from the language switch
itself. We measure the two causes separately and fix the spelling part with a
training-free, CPU-only phonetic normalizer.

Working title: **"Spelling, Not Switching: Disentangling Romanization Noise in
Hinglish Code-Mixed Information Retrieval"**

## 3. Base paper and the gap
**Base:** Zeng, Lu, et al. "Code-Switching Information Retrieval: Benchmarks,
Analysis, and the Limits of Current Retrievers." arXiv:2604.17632 (Apr 2026).
Code: github.com/paddler2022/Code-Switching-Information-Retrieval
- What they built: CSR-L (human-rewritten zh/ja code-switched queries over BEIR) and CS-MTEB (LLM-generated, 9 languages).
- What they found: drops of up to 27%. Multilingual models are more robust but still drop. Code-switched queries move away from monolingual queries in embedding space.
- Their fix: **lexicon-based vocabulary expansion** using the MUSE bilingual lexicons (Conneau et al. 2018). New token embeddings are set to the average of their translations' subword embeddings. This recovers only part of the drop.

**Gaps we fill:**
1. No Indic language and no **romanized** code-mixing in the base paper.
2. Their lexicon fix assumes **one spelling per word**. Romanized Hindi has no standard spelling, so exact lexicon lookup misses most real variants.
3. They cannot separate the effect of switching from the effect of spelling, because in their languages each word has a fixed spelling.

## 4. Research questions
- **RQ1:** How much do modern retrievers drop on romanized Hinglish queries compared with the English originals?
- **RQ2 (core):** How much of that drop comes from the switch itself (clean Hinglish), and how much comes from spelling variation (noisy Hinglish)?
- **RQ3:** Does a training-free phonetic-key + lexicon normalizer recover the spelling-induced drop better than the base paper's vocabulary expansion? How close does it get to an LLM translation ceiling?

## 5. Contributions (as they will be stated in the paper)
1. **Hinglish-CSR**, a romanized Hinglish code-switched query set over 3 BEIR datasets, with controlled spelling-noise levels (0 / 25 / 50%) and a human-verified subset.
2. A **controlled disentanglement** of switching vs. spelling degradation across lexical, English-only dense, and multilingual dense retrievers.
3. **PhonoNorm** (working name), a training-free CPU normalizer: rule-based phonetic keys plus a romanized bilingual lexicon. It recovers X% of the spelling-induced gap at near-zero cost.

## 6. Data
### Corpora (small BEIR sets, chosen to fit CPU)
| Dataset | Docs | Test queries | Note |
|---|---|---|---|
| SciFact | ~5.2k | 300 | science claims |
| NFCorpus | ~3.6k | 323 | medical/nutrition |
| ArguAna | ~8.7k | 1,406 → subsample 300 | argument retrieval (overlaps the base paper's Touché domain) |

Excluded: TREC-COVID (171k docs) and Touché (300k docs), because they are too large to encode on CPU within the timeline. State this as a limitation.

### Query variants per English query
- **EN:** original English query.
- **CS-clean:** natural romanized Hinglish rewrite generated by Groq (Llama-3.x-70B or similar), using a prompt adapted from the base paper's Appendix D. Hindi words use the most common romanized spelling.
- **CS-noise25 / CS-noise50:** CS-clean with rule-based spelling perturbations applied to 25% / 50% of the **Hindi tokens only**. English tokens stay unchanged, so the noise affects only the romanized part.
- **EN-noise (control):** English query with comparable character noise. This checks that any extra drop is specific to romanization, not generic typo sensitivity.

### Spelling-variant operators (documented and reproducible; fixed random seed)
- Vowel deletion: nahi→nhi, kya→kya (no change if no medial vowel), mujhe→mjhe
- Long/short vowel swap: aa↔a, ee↔i, oo↔u (kaam→kam, theek→thik)
- Final h / nasal variation: hai→h / hy / he; nahi→nahin
- Consonant alternations: w↔v, z↔j, ph↔f, sh↔s
- Final vowel drop/add: karna→krna, accha→acha→achha

Noise is injected only into the words the LLM reports as Hindi (`hindi_words` in its JSON output), **never** into words picked by our own tagger. Using our tagger would give PhonoNorm a circular advantage.

Deferred (stretch, not in the plan): compare variant frequencies with a real Hinglish corpus (L3Cube-HingCorpus) to argue that the noise is realistic.

### Human verification (user, ~100-150 items)
- Sample about 120 CS-clean queries, stratified across the 3 datasets.
- Two labels per item: (a) natural Hinglish? yes/no; (b) meaning preserved? yes/no; plus an optional rewrite.
- Report the acceptance rate, as the base paper and the sarcasm paper did. Keep the rewrites as a human-verified test subset and report results on it separately.

## 7. Method: PhonoNorm (the tweak)
Pipeline applied to the **query only**. The corpus is not changed.
1. **Token language ID:** a simple heuristic (English wordlist + Hinglish lexicon membership) marks each token as EN or HI.
2. **Phonetic key** for HI tokens: lowercase, map digraphs and aspiration (ph→f, kh→k...), unify consonant alternations (w/v, z/j), strip a final nasal, collapse doubled letters, and drop non-initial vowels. The output is a consonant-skeleton key; for example, nahi/nahin/nhi → `nh`. A **coarse key** (which also drops non-initial h and y) is the fallback for variants like nai and kia. Exact rules are in implementation plan Task 3.
3. **Romanized lexicon:** start from the MUSE hi-en lexicon (the same source as the base paper, for a fair comparison). Transliterate the Devanagari side to Roman with `indic-transliteration`, compute phonetic keys, and map each key to its English glosses. Lookup cascade: exact → key → coarse. (Mining extra pairs from PHINC is deferred and not in the plan.)
4. Hinglish function words (from a curated stopword list with spelling variants) are dropped rather than glossed.
5. **Rewrite:** replace each HI token whose key is in the lexicon with its top English gloss, using frequency order to break ties. Keep the tokens that can't be resolved.
6. **Ablation ladder** (exact mode names): `none` → `stop` (drop HI stopwords only) → `exact` (exact lexicon lookup ≈ the base paper's lexicon idea at query level) → `key` (full cascade) → `key_expand` (append glosses instead of replacing them).

## 8. Retrievers (all run on CPU)
- **Lexical:** BM25 via `bm25s` (pure Python, fast; no Java needed)
- **English-only dense:** all-MiniLM-L12-v2 (the base paper used it)
- **Multilingual dense:** multilingual-e5-small; bge-m3 (568M; run it on all 3 datasets if encoding time allows, otherwise SciFact + NFCorpus only)
- Arctic-Embed-m-v2.0: dropped (YAGNI). Add it only if there is spare time.

Cache corpus embeddings to disk once per model.

## 9. Baselines and comparisons
| System | Role |
|---|---|
| No normalization | measures the drop |
| **Vocab expansion (base paper §6)** reimplemented for MiniLM with the romanized MUSE lexicon | main prior-work baseline |
| Back-transliteration to Devanagari (IndicXlit or `indic-transliteration`) | alternative cheap fix (multilingual models only) |
| **PhonoNorm** (+ ablations i-iii) | ours |
| **Groq LLM translate-to-English** | upper-bound ceiling; run only on CS-clean and CS-noise50 to save free-tier calls; reported as costly (latency/cost per query), not as our method |

## 10. Metrics and analysis
- **Primary:** nDCG@10. **Secondary:** Recall@100.
- **Gap recovery** = (Norm − Noisy) / (EN − Noisy), in %.
- **Decomposition:** total drop = (EN − CS-clean) [switching] + (CS-clean − CS-noiseK) [spelling].
- **Significance:** Fisher randomization test over queries via `ranx`, α=0.05, for the main comparisons.
- **Embedding analysis**, mirroring the base paper's Fig. 2: cosine similarity between EN and CS query embeddings (and their centroid distance), before and after normalization. A cheap and convincing figure.
- **Error analysis:** 5-8 qualitative examples where PhonoNorm fails, such as ambiguous phonetic keys (e.g. `KL` = kal 'yesterday/tomorrow' vs kaal 'time/death').

## 12. Novelty risks and mitigations
- **Gupta et al. 2014 (mixed-script IR query expansion)** covers similar ground for pre-neural IR. Mitigation: our contribution is the controlled spelling-vs-switching decomposition on modern dense retrievers, plus a direct comparison with the 2026 vocabulary-expansion fix.
- **FIRE CMIR shared tasks** (Bengali-English, romanized). Mitigation: cite them. They use social-media QA, not controlled BEIR-based measurement.
- **Synthetic queries** are a common reviewer complaint. Mitigation: the human-verified subset plus separate results on it.
- **Result risk:** if PhonoNorm doesn't help dense multilingual models, the decomposition finding is still the main contribution, and the negative result is reported honestly.
- Before writing, run a final novelty search (Semantic Scholar / ACL Anthology) for "Hinglish retrieval spelling variation dense".
